# Running the disposable fresh-install controller

This runner is for a fresh, explicitly disposable RHEL 9 VM only. It cannot
qualify a private 144/21 upgrade, catalog migration, daemon import, physical
LTFS, or backup/restore. Local fixtures do not qualify a release. The real
signed-artifact VM smoke and independent restoration review remain required.

Prepare the VM and its OS dependencies before capturing the baseline. The
supported profile is deliberately narrow: local `qemu:///system` or
`qemu:///session`, a running guest with QEMU guest agent, exclusively private
ordinary local qcow2 disks, no real backing chains, no network interfaces by
default, no passthrough/shared devices or QEMU command-line overrides, and no
separate NVRAM. Libvirt's exactly empty terminal `<backingStore/>` is supported.
Supported host character connections are libvirt PTYs and the generated
QEMU guest-agent Unix socket; arbitrary host character devices are refused.
The supported profile is headless and refuses other device types. Libvirt must support an
atomic internal snapshot of both running memory and every disk. Unsupported
storage is refused. Explicitly place the following namespaced marker in the
domain XML; a name or description containing “disposable” is insufficient:

```xml
<metadata>
  <lto-disposable-test xmlns="urn:lto:disposable-test">true</lto-disposable-test>
</metadata>
```

Controller prerequisites are Python 3.11.8 or later, `virsh`, `git`, and all
tools required by the selected release verifier. The guest additionally needs
the same verifier tools (`rpm`, `rpmkeys`, `gpg`, `gh` and its approved cached
Sigstore trust/bundle material), Python 3.11.8 or later, tar support in Python,
dnf, systemd, enforcing SELinux, openssl, and every application/runtime/driver
OS dependency already installed. The runner does not enable repositories or
install missing dependencies. The verified attestation bundles must be usable
without guest networking if choosing the default no-NIC profile; do not supply
user tokens or weaken verification. Offline attestation operation is unverified.
No tape or SCSI-generic devices may be present.

If the selected existing verifier needs networking, supply both optional
`--test-network-name EXISTING_NAME` and `--test-network-uuid EXACT_UUID` for a
separately designated existing libvirt managed NAT network. The sole guest NIC
must be `type=network` and reference that exact name. Any runtime `bridge`
attribute must match the selected managed bridge and any `portid` must be a
canonical UUID; extra source attributes fail. The controller requires
matching active/persistent network definitions and UUID, active NAT mode,
libvirt's managed `virbr` bridge, no explicit physical forward device or
virtual-port/driver override, and no other domain referencing that network.
Bridge/direct/hostdev/vhostuser NICs are refused. The runner does not create or
change networks, firewall rules or provisioning. NAT does not certify egress
isolation from LAN or production systems; network selection and any real
execution remain separately designated by the user. No offline verification
protocol is introduced, and the pinned verifiers remain unchanged.

Select the reviewed clean application and driver tag checkouts matching the
candidate tuple (app 0.11.31-155, runtime 0.11.27-3, driver 0.1.2-22).
The application and driver source tags are approved and published, and their
hosted unsigned build comparisons passed. Final signed-asset approval and
actual disposable-VM smoke acceptance remain pending.
Verifiers are loaded only from the explicitly selected and pinned
source checkouts, never from an implicit fallback.
The approval JSON is the existing Task 2 `FRESH_INPUT_KEYS` object, with its
exact app/driver source commits, tags, repositories, signed asset hashes,
public-key fingerprints, driver approval file/hash, and driver verifier hash.
The controller requires the exact approval-file SHA-256 plus explicit pins
for the selected application's release verifier, fresh-host checker and smoke
report validator. Compute and review these pins outside the smoke; no approval
file or signing key is generated by this runner.

```bash
python3 packaging/rpm/run-public-fresh-vm-smoke.py \
  --libvirt-uri qemu:///session --domain DESIGNATED_DISPOSABLE_DOMAIN \
  --app-candidate /absolute/approved/app-candidate \
  --driver-candidate /absolute/approved/driver-candidate \
  --app-tag-source /absolute/reviewed/app-tag \
  --driver-tag-source /absolute/reviewed/driver-tag \
  --approval /absolute/approved/fresh-inputs.json \
  --approval-sha256 APPROVED_64_HEX \
  --app-verifier-sha256 APPROVED_64_HEX \
  --fresh-host-sha256 APPROVED_64_HEX \
  --report-verifier-sha256 APPROVED_64_HEX \
  --timeout-seconds 600 --report /absolute/controller/new-smoke.json
```

All libvirt and guest-agent operations after selection address the domain
UUID. The controller checks the marker and storage again before mutation and
restore, captures its baseline before snapshot creation, verifies exact
snapshot identity/coverage, then transfers one hashed archive. Links and
special files are refused in staged sources/candidates; reviewed checkouts
must have ordinary `.git` directories rather than worktree `.git` links.
The guest repeats real Task 2 signed/attested input admission from the pinned
whole source checkouts before installing driver, runtime, then application.
Only the driver's absolute approval-file location is remapped into private
guest staging; its exact byte hash and all approval identities are preserved.

The guest uses the installed WebUI executable, runs an ephemeral loopback TLS
service under `lto-web`, generates only disposable test credentials inside
the VM, and proves login with CSRF, an authentication redirect, session cookie,
and a protected account request. This exercises the installed WebUI launcher
and authentication, not production network binding/firewall configuration.
It validates settings through isolated installed runtime paths and requires
the complete installed hardware-preflight JSON with `devices.stable=false`
and exit 2. The real preflight emits `config.valid=false` only on a settings
error, so a standalone configuration failure cannot count as hardware refusal.
No daemon-mediated import is attempted or claimed.

Package NEVRAs, payload verification, source-identical notices/runtime SBOM,
systemd unit syntax, service-account separation, enforcing SELinux/policy and
file labels are checked before the runtime observations. Package erase is
followed by actual inventory: generated paths are recorded and preserved,
owned executable paths must be absent, and managed units must be inactive.
Generated auth/configuration/account state is not manually erased.

The defined baseline covers content, type, mode, UID/GID and link targets for
`/etc` and `lto*` entries under `/var/lib`, `/usr/bin`, `/usr/libexec`,
`/usr/lib/systemd/system` and `/usr/share/selinux/packages`; it also covers the
complete RPM inventory, LTO unit inventories, enforcing state and policy-module
inventory. Timestamps, volatile logs, `/run`, staging in `/var/tmp`, unrelated
`/var/lib` data and disk byte equality are outside this digest. The internal
memory/disk snapshot is the rollback mechanism; digest equality verifies only
the defined observable baseline, not every possible guest state.

The guest streams command diagnostics into private stage files as commands
run; command timeouts preserve their captured partial bytes. The controller
incrementally fetches those files through UUID-bound QGA file transport and
performs a final bounded fetch before restoration, including failed/ongoing
commands. Evidence files record whether the guest exited, retrieval failures,
and retained byte counts. A stalled process has a partial transcript even when
every available byte was fetched; complete evidence is not claimed. Per-fetch
chunk/time/size limits bound retention. Missing or unreadable diagnostics make
the attempt unqualified and never skip restoration.

On failure, timeout, SIGINT or SIGTERM, the controller retains private raw
evidence and attempts restoration of the exact unique snapshot, including
ambiguous snapshot-create outcomes. The guest may still run after a transport
timeout; restoration, not termination of `virsh`, removes its mutations.
Repeated signals are ignored during recovery. SIGKILL, controller/hypervisor
crash, inaccessible storage and a failed restore require operator recovery
from the retained snapshot identity and evidence. Snapshots are retained;
none are deleted automatically. No report claims success if restore fails or
the observed baseline differs.

The new sanitized report and a private mode-0700 sibling evidence directory
stay outside the guest. The report is schema 2 and always lists
`backup_restore`, `daemon_import`, and `physical_ltfs` as unverified. Failed
attempts retain partial checks with `qualified=false`; they are not admissible
release evidence. A fully observed report is additionally passed to the exact
pinned existing smoke-report validator. Review the private transcript and
snapshot proof independently before authorizing any release action.
